# Adoption trials: not yet validated

No external developers have trialled these prototypes. GitHub source and alpha distribution were authorized and published on 5 November 2026; npm registry publication and outreach remain separate actions. The numbers below are targets, not observed results.

Deployproof is the first onboarding experiment: its [README](https://github.com/CVamsi27/deployproof#readme) leads with a synthetic broken/fixed demo, and its [pilot guide](https://github.com/CVamsi27/deployproof/blob/HEAD/docs/pilot.md) includes an opt-in report form and blank trial CSV. Launch messages are drafts only. No participant or retained use is inferred from these materials.

## Protocol

The owner selected GitHub-package installation on 5 November 2026; npm publication is deferred. Deployproof's [real pnpm example](https://github.com/CVamsi27/deployproof/tree/HEAD/examples/pnpm) prepares actual pnpm 11.23.0 deployments with four synthetic controls. Retryglass's [README](https://github.com/CVamsi27/retryglass#readme) starts from its installed GitHub package. These maintainer checks improve trial readiness; they do not count as participants or independent integrations.

Recruit five independent developers for each candidate through user-managed outreach. Give them the package and README, without a live walkthrough. Record the package revision, OS/runtime, task start and end, commands tried, assistance needed, and the first actionable finding. Use a synthetic or consented non-production case; never collect credentials, environment files, proprietary source, or customer records.

The intended integration task is: declare a synthetic same-job retry rehearsal; check an actual deployment folder; bind one application contract to the rollout runner; or add one retained-WebSocket revocation case to an existing Playwright suite. Record fixture setup separately from the tool's execution time. At the next relevant code change, ask whether the developer reran or retained the tool and why. Two weeks without a relevant change is unobserved, not removal or success.

## Promotion rule

Targets per candidate: three of five complete their integration and two retain/rerun it on a later change. Also require actionable diagnostic evidence and passing technical gates for the claimed scope. A failed integration or decision to remove the tool is useful counterevidence. Do not treat downloads, stars, a successful demo, or a warm synthetic runtime as retention or time saved.

Where the baseline or an existing tool reaches the same outcome with equal or less effort, prefer contribution or stop the standalone project. Where setup dominates, fix that obstacle before adding adapters. Promote candidates independently; do not turn three experiments into a shared platform.
